# cross_exchange_mm 修复与上线准备方案

日期：2026-11-01。代码基线：`aebc6a4ae0726734acf24b2661d284553cd2adb5`。

状态：**设计方案，尚未实施或验收。** 依据[本轮审查及复现证据](verification/2026-11-01/cross-exchange-mm-review/README.md)。本方案不改变现有实盘授权范围。

目标：先消除已有挂单风控与故障上报缺口，再完成平台双账户执行准入，最后验证执行稳定性和成本后的收益。策略保持单文件；账户事实、保证金预占、执行一致性、恢复及持久化继续由 Rust 平台负责。

## 1. 分期交付

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| A：策略缺陷修复 | 持续报价准入、最小成交可对冲检查、公开观测及关键内嵌场景 | 四个审查探针改为验证正确行为；Python 与真实原生回调通过。此时仍不能上线 |
| B：平台交易闭环 | 多绑定风险与资金预占、显式故障排空、绑定预检、timer/停止配置 | 原生宿主、离线执行器和管理入口使用相同规则；双账户模拟及故障矩阵通过 |
| C：策略验收与发布 | 双所真实行情回测、独立撮合、成本敏感性、冻结发布包 | 执行与收益分别出具证据；随后才进入另行授权的受控实盘 |

保持现有单市场受控门禁，直到 B 的替代实现及负例通过。阶段 A 的修复不能通过关闭 `execution_limits` 提前上线。

## 2. 持续检查已有挂单，而不只检查新挂单

主要修改：[cross_exchange_mm.py](../strategies/cross_exchange_mm.py) 的 `drive`、`quote_side`、`drive_hedge`。

把现有报价路径拆成两个明确步骤：

1. `audit_quote_safety`：对持仓、现有 maker 单、在途 hedge、同回调候选命令检查安全约束；所有市场、账户、成交、订单、timer 事件都执行。
2. `maintain_quote_price`：安全条件通过后，才决定是否按价差阈值和最小间隔调整价格。

`min_requote_ns` 只限制普通价格更新。金额超限、最小成交不可对冲、行情失效或对冲预算失效必须立即请求撤 maker 单。已有订单分支不再跳过安全检查。

计算使用订单**未消费/未确认释放的剩余量**，不能直接套用完整 `order_qty_lots`；CancelPending、结果未知和终态等待成交的引用继续占用预算。纯粹请求撤单不释放预占。

每次至少检查：

- maker 的最坏单边持仓及金额；hedge 的独立持仓与金额。
- 双腿可能成交后的基础币 delta 区间；两所总仓位不能净成零后忽略单所风险。
- 对冲方向的新鲜可执行价格、可见数量、保护价、费用和最小成交约束。
- 现有挂单与同批新增命令的合计占用；不能在两个 `quote_side` 调用间重复使用同一预算。

这里必须区分**准入上限**和**行情变化后的风险观测**：价格跳跃可能让既有持仓的盯市金额瞬间超限，任何算法都不能保证市场变化本身永不越线。正确反应是及时关新增风险、撤单并按预定预算处置，而非忽略超限或扩大限额。

验收：在重报价限频窗口内移动价格，旧报价立即进入撤单；已有 maker 金额超限被观测并触发规定动作；撤单期间迟到成交仍按真实事实处理。

## 3. 为成交后的 hedge 预留能力，并定义尾量处置

单纯把金额检查移到 `return` 前，只能减少风险窗口，不能消除撤单竞态。需要在 maker 下单前由平台预留该订单可能触发的对冲资源。

### 3.1 报价额度与硬性执行额度

在实例风险配置中明确区分：

- 正常 maker 报价额度：低于硬性执行上限，为价格变化和取消竞态保留空间。
- hedge 预占：覆盖 maker 剩余量可能成交后需要的对冲数量、费用及逐所保证金。
- 独立救援额度：固定最大数量、金额、允许成本、保护价和绝对期限，仅处理已知成交及其退出。

所有额度启动前冻结、绑定风险配置修订并进入恢复身份。救援额度属于事先授权的硬性执行预算，不是在亏损后自动加码。超出预先定义的压力价格范围或硬性上限时，不能承诺继续对冲，转入有界退出或人工处置。

### 3.2 每个原生最小成交都要可处置

平台从原生元数据验证：

`一个 maker lot 的基础币 delta = r × 一个 hedge lot 的基础币 delta`

首版继续要求 `r` 为精确正整数，并分别核对原生最小量、最小金额和合约乘数。不能放大 maker lot 来掩盖真实小额部分成交。

正常报价要求：在配置的保守价格范围内，每个 maker 最小部分成交均满足 hedge 的下单量和最小金额约束。金额计算、价格取整和比较使用平台精确十进制/整数比例；不以二进制浮点近似作为最终准入证据。

### 3.3 撤单后仍成交的兜底

按顺序处理：

1. 停止新增 maker，撤销剩余 maker，保留在途预占。
2. 使用已预留额度对冲已知欠量，沿用原价格锚和原绝对期限。
3. 若 hedge 最小金额不满足，在原期限内可合并自然到达的已知成交；不得为了凑单再主动增加 maker 仓位。
4. hedge 已证明未在途且尾量无法交易时，可执行预先配置的 maker 原腿 reduce-only 回退，数量不超过明确归本策略所有且可平的持仓；新建独立退出订单引用，保留完整成交/终态/持仓确认。
5. 原腿也不满足交易所最小要求，或 hedge 结果未知时，不能假设可安全平仓；明确暴露残留量、冻结新增动作、保留占用并请求人工处置。

因此，首个生产风险配置应选择最小部分成交在对冲所可交易、且预定原腿回退可执行的组合。不满足这一条件的组合拒绝准入；不能宣称所有交易对都能自动清理尾仓。

## 4. Rust 平台实现真正的多绑定准入

主要位置：`titan-strategy-runtime` 的 `model.rs`、`runtime_v13.rs`、`offline_v13.rs`，`titan-account-service` 的账户/执行与预占接口，以及 CLI 管理配置与 `management/control.rs`。

### 4.1 保留旧规则，增加显式多绑定配置

新增独立的多绑定受控执行配置，与旧 `execution_limits` 互斥；旧单市场实例继续走原路径。新增能力声明和版本校验，旧宿主拒绝自己不理解的新能力。

多绑定配置至少包含：

- 每个 `(account, asset, position_side)` 的执行身份、原生单位、数量/金额/价格/行情年龄限制。
- maker/hedge 角色、基础币 delta 等价关系、共同报价单位与汇率来源。
- 每个账户抵押域的保证金、费用、压力缓冲和预占预算。
- 总裸露区间、最大持续时间、救援预算、停止与退出策略。
- 原生元数据摘要、风险配置修订和允许的订单/TIF 能力。

将 `last_bbo_ns` 等单市场状态改为按市场维护。不能用 maker 的新鲜行情证明 hedge 行情新鲜，也不能把两个市场的 ticks/lots 直接相加。

### 4.2 共用风险计算

以已证明的持仓锚和独立成交推进预期库存；对尚未投影到持仓的已知 fill 只记一次。每条腿的可成交区间保守计算为：

`Q_min = P - 未释放卖单剩余量`

`Q_max = P + 未释放买单剩余量`

再按精确基础币比例求双腿 delta 区间，以及逐所最坏持仓、金额和保证金。包含本回调暂存命令、未知单、CancelPending 和等待成交确认的终态订单。跨所盈利不抵消亏损所的可用保证金或清算缓冲。

平台按确定的账户锁顺序一次核对并预占两侧资源，再持久化、派单；同一抵押域内其他占用也计入。本机预占原子性不等于交易所之间存在原子成交。

在线宿主、离线执行和恢复共用计算器及规则；策略做快速业务检查，Rust 平台保留最终准入权。

### 4.3 成交先于持仓时必须仍能合法 hedge

当前 `InventoryProof::validate_opening` 会在持仓未确认时拒绝所有非 reduce-only 提交。跨所 hedge 可能在第二个账户开仓，不能只删除多市场限制后继续复用该全局阻断条件。

新增明确的命令用途及平台证明：

| 用途 | 平台允许条件 |
| --- | --- |
| 新 maker 风险 | 必要账户/库存证据就绪，双腿资源预占完整 |
| 已知成交 hedge/救援 | 独立 fill 已证明、原始意图和剩余义务匹配、使用未耗尽预占、所有硬性限制仍通过；可容忍匹配的持仓推送滞后 |
| 原腿/持仓退出 | 持仓身份、方向、可用数量和活动预占均有证明，使用真实 reduce-only |
| 撤单 | 身份和所有权合法，不依赖新鲜市场价格 |

用途标签由预先绑定的执行角色和平台事实复核，不能由策略随意写一个“hedge”标签就绕过风控。未知 hedge 必须查原身份，不能借另一用途重发。

预占、意图、提交结果未知、成交消费和释放边界进入现有恢复机制；跨进程恢复不得重置额度、期限、代次或未知订单身份。

## 5. 故障上报与安全排空使用独立语义

主要位置：策略、SDK/编译包装器、V13 instance/staging、原生宿主、离线执行器、公开观测与管理状态。

不把所有 `mm.error` 直接改成 `return -1`，因为现有宿主会丢弃失败回调暂存的撤单。

建议新增需要显式能力协商的业务返回结果：保留 `0` 成功、负值 ABI/执行错误；约定范围内的正值表示锁存业务故障码。宿主将这种结果与“回调执行失败”区分，允许验证和提交合法安全命令。该通道不复用 `last_error_code`，不随意占用保留内存字段；优先保持现有 V13 内存布局，更新能力与返回语义。

业务故障发生后的顺序：

1. 立即锁存原因，禁止新增 maker 风险，进入故障排空。可复用宿主 `Stopping`，附带不可丢失的故障原因和原期限。
2. 独立校验本回调只含合法撤单、已授权 hedge/救援或退出；持久化状态与意图，再派发安全命令。
3. 排空期间继续接收订单、独立成交、持仓和 timer；仅按冻结预算行动。未知执行冻结对应身份并交平台对账。
4. 排空完成后以原故障结束为 `FAILED`；不能因为仓位归零把本次失败改记成功。超时或残留同样明确 `FAILED`，并保留残留风险与占用。
5. 即便策略执行结束，平台账户观察和原身份对账仍负责接收迟到事实；不因进程退出释放账户占用。

持久化失败、ABI 错误等平台硬故障仍保持既有失败关闭规则，不能借业务排空继续发送新风险。必要撤单走已有安全能力，并明确记录发送结果，不以“已请求”冒充撤销成功。

公开业务观测至少包含：阶段、首个故障码/时间、停止原因、maker 与 hedge 库存、欠量、在途数量、原敞口期限、尝试次数、毛收益、行情时间和待人工处置标记。账户净权益、费用、资金费、实际持仓继续来自平台事实，不由策略重建第二套账本。

验收：同一原生回调触发故障并产生撤单时，撤单真实进入命令提交；管理侧及时可见故障排空；迟到 Start/Resume 不得重开新增风险；重启后故障和预算保持。

## 6. 强制运行前提与清晰的停止策略

### 6.1 启动预检和完整模板

提供 `configs/cross_exchange_mm.example.toml`，只含账户/密钥引用，不含凭据。预检失败拒绝启动：

- 两个原生账户/市场身份和线性 NET 模式正确，策略需要的 PostOnly、IOC、独立成交与查询能力已验收。
- 共同经济资产、tick/lot/乘数、原生最小约束及报价币转换有证据；首版优先同报价/抵押币，缺少可靠 FX 的跨币组合不准入。
- 两所初始事实满足 Fresh 或明确的恢复规则；资金与救援资源可预占。
- 多绑定风险配置齐全；周期 timer 必填，且有平台最大调度延迟监测。不能仅声明 TIMER 能力而未实际配置调度。
- 编译参数、风险配置及实例绑定之间的数量/金额、期限和退出能力一致。

timer 周期可在模拟环境从 100 ms 开始测量，但不作为未验证的生产 SLA；同时测事件队列、SQLite 提交和调度延迟。定时器过载触发健康故障，不能让超时检查无限排队。

### 6.2 停止目标与账户占用

保留已有普通 Stop 的 `DrainHedge` 语义，明确展示“完成对冲并留仓”。需要留仓时，平台必须保留风险所有者/占用，或原子移交给明确的留仓管理者；不能仅因运行停止就当作账户空闲。

新增明确的 `FlattenOwned` 退出目标：撤 maker，核清在途订单，按双腿独立预算逐步平掉本策略所有持仓，等待两腿订单终态、原生成交和持仓归零后才完成。它需要独立退出引用和状态，不能把 hedge 简单改成 reduce-only，也不能在有未知订单时假设安全清仓。

生产风险配置必须显式指定亏损/保证金风险触发后的动作。建议首个自动运行配置要求风险停止使用已验收的 `FlattenOwned`；人工 Stop 可以继续选择 `DrainHedge`。退出失败或尾仓不可交易时保留风险与占用，不宣称最大损失得到保证。

### 6.3 期限预算

分别配置撤单、已知欠量 hedge、原腿回退/双腿退出和事实确认预算，受宿主总 Stop deadline 约束：

`撤单预算 + 必要退出预算 + 确认/持久化预算 + 安全余量 <= 宿主总停止预算`

真实执行允许部分阶段重叠，但不能以可能重叠为由省略最坏路径验证。已有欠量继续使用其原绝对期限；Stop、重试和恢复取更严格期限，不能重新计时。

当前管理路径 Stop 不超过 10 秒。先在该约束内设计并压测配置；达不到就拒绝该配置。若确需修改管理总期限，作为单独的平台契约变更处理，不能在策略内部偷偷延长。

## 7. 版本与恢复

- 仅修复报价分支、未改状态布局的阶段 A，可发布 `2.0.1 / schema 2`，仍生成新产物摘要；旧检查点不得因 schema 相同就跨产物直接恢复。
- 新增故障阶段、退出引用、额度/期限等持久业务字段后，建议发布 `2.1.0 / schema 3`，重新编译签名。具体版本在实施冻结时确定。
- 新能力先更新 Rust 宿主、SDK、编译器元数据、在线/离线加载与管理验证；旧宿主必须拒绝新能力。
- 首版不自动迁移旧运行。使用旧产物按旧规则完成停止/对账，妥善处理留仓与占用，再启动新版本；无法证明旧运行安全结束时不新建 namespace 绕过。
- 状态、意图和预占恢复需要共同证明原始身份及消耗水位；公开观测不作为恢复证据。

## 9. 验收矩阵与环境

必须覆盖以下结果，而非仅断言某函数被调用：

| 场景 | 通过标准 |
| --- | --- |
| 限频期间价格使两腿金额超限 | 立即关新增并撤单；迟到成交使用预留资源或明确退出 |
| 单 lot 不足 hedge 最小金额 | 不再维持该报价；竞态尾量退出或明确残留，不能凑大订单 |
| maker fill 先于 position | 原生宿主依独立成交和预占允许唯一 hedge，不要求伪造 reduce-only |
| 对手 maker fill 与 hedge cancel/fill 交错 | 库存、在途区间和反向修正正确，未知结果不重复下单 |
| 两所价格/单位/币种不同 | 各腿独立估值，非法比例或过期 FX 拒绝 |
| 账户资金不足、费用未知、抵押域共享 | maker 提交前拒绝或降至合法量，不透支另一腿准备金 |
| 业务故障与撤单同回调 | 故障可见且必要撤单提交；最终保留失败原因 |
| 无行情、timer 缺失或严重迟到 | 缺失配置不启动；沉默期间期限仍生效，过载明确失败 |
| intent/预占提交前后或传输后崩溃 | 只恢复原身份；未知不重发；原期限、额度消耗和占用不回退 |
| DrainHedge / FlattenOwned | 留仓和零仓分别证明；迟到成交不提前完成 |
| 磁盘满、SQLite 超时、队列饱和 | 停新增、保留事实与未知量，不伪造关闭或完成 |
| 大幅价格跳跃超出既定救援范围 | 不扩大硬额度；按约定退出或暴露人工处置状态 |

本地只编写、审查、修改源码和文档。全部格式、Clippy、Rust/SDK/原生编译与测试、撮合/故障/压力和回测在 `titan-build` 的隔离目录执行；同步前确认远端版本与工作区，冻结输入清单，防止旧构建缓存误用。
