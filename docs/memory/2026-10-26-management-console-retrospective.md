## 应该避免的问题

### 只验证正常完成顺序

参数复制先请求 B、后请求 A 时，B 的迟到响应仍可能覆盖 A。底层查询丢弃过期响应后正常返回，调用者还会继续写入模板、参数和草稿；只在查询层加保护不够。

以后凡是异步读取后修改表单，都要同时检查请求代次、会话、组件存活和当前输入。等待下一次渲染后仍需核对目标。回归应主动倒置响应顺序，并覆盖用户继续输入、切换会话和关闭页面，而不是只等待请求依次完成。

### 让多个组件替换同一份全局选择

工作区和嵌入运行详情都调用全量替换式的固定资源接口。参数页编辑会清掉运行详情对部署记录的固定，历史事件增长后，风险上限和部署来源随缓存淘汰而丢失。单组件缓存测试无法发现这个冲突。

固定资源必须有明确所有者。各组件只更新自己的有限集合，Store 汇总，组件销毁时释放。测试需要把工作区、运行详情和大量后续事件放在同一场景中；本轮修复后用 600 条部署事件验证了这一点。

### 把返回分页误当成查询工作量有界

研究目录虽然只返回一页，但原实现会持有管理数据库的共享互斥锁，读取和反序列化全部历史资源，最后才分页。历史越多，普通资源读取和控制受理等待越长。

查询应单独审查读取字段、锁持有范围和执行线程。修复采用既有 SQLite WAL 的独立只读连接、阻塞任务线程及授权与引用字段投影，仅为最终授权分页加载完整资源，没有增加数据库表或服务。

在 12,000 条、每条 32 KiB 元数据的模拟历史下，目录查询由约 1.061 秒降至 0.347 秒。修复前并发资源读取等待约 0.961 秒；修复后的并发探针同时覆盖资源读取和草稿写入，最长约 0.102 秒。两次并发探针操作组合不同，这些数值用于确认阻塞问题及修复效果，不作为生产延迟承诺。

### 只校验标识的输入片段

配置允许 128 字符的研究 ID，加上 `research-` 后却超过接口上限，形成目录可见、进入后查询失败的工作区。边界校验必须作用于最终组装结果。

本轮明确显式配置最多 119 字符，并测试最终 128 字符身份可查询、超出边界的配置被拒绝。路径、文件名、复合键和其他带前缀的标识也应采用同一原则。

### 在验证启动后才补齐环境和证据

本轮 Rust 原生编译测试曾因遗漏 SDK Python 环境失败；补齐既有环境后才完整通过。类似的环境准备反复可以避免。

验证开始前，应一次确认远端目录与版本、工作区状态、Python 与 SDK 路径、Cargo 镜像和离线缓存、浏览器路径及固定产物。调用 CLI 前读清参数语义，例如类型导出入口接收目录。同步和证据归档使用明确文件清单，持续更新最终汇总，避免目录名称、旧日志或先前通过记录被误认为当前版本证明。

## 值得保留的做法

### 先确定业务组织方式和视觉方向

先完成运行总览与策略详情的高保真设计，让视觉讨论有具体对象。信息架构也应尽早围绕实际工作流程整理：策略研究包含参数、编译、回测和报告，策略实盘引用固定产物，账户风险保持账户视角。这样更容易确定导航和模块边界，减少按接口资源名称拆页面带来的后续整合成本。

### 共用能力保持一个实现

研究工作区只负责归集和展示，实盘详情继续复用同一个组件。交易事实、风控、停止和恢复仍由平台与引擎确认；前端没有复制账本或生命周期判定。这使界面结构调整能够限制在展示和查询范围内。

### 先复现再修复

四项审查问题都先明确触发条件，再用实际 Vue 组件、Pinia、缓存函数或管理程序复现。修复后把关键场景保留为仓库回归测试，既解释了问题，也约束了后续修改。故障探针遗漏研究身份时，修正测试配置，继续保留生产身份校验。

### 用源码与产物身份串起验收

新目录保留旧验收现场；服务器重新构建程序，从同一程序导出 DTO，再构建配套前端。最终交付的 60 个源码文件与服务器验收清单一致。代码、生成类型、原生程序和前端产物应成套管理，不能混用不同轮次的结果。

## 后续执行顺序

1. 修改前写清资源身份、归属、所有者及异步取消条件，确认业务模块之间的唯一职责。
2. 写实现时同时补关键边界回归，优先覆盖请求乱序、多组件共享资源、历史增长和最终标识长度。
3. 在编译服务器先检查环境与源码身份，再执行对应静态检查和测试；耗时构建与受控运行验证顺序执行。
4. 按本轮影响重跑相关 M1/M2/M3 流程，区分模拟验证与真实账户验证。
5. 归档最终版本的结果、清单和截图，再提交代码；长期规则进入[工程经验](engineering.md)，当天经过和反思保留在复盘中。

最需要改进的是把边界审查前移。主流程通过后继续做独立审查是有效做法，但不应让它成为首次考虑请求乱序、资源所有权和控制阻塞的时点。
